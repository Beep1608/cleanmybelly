## 1. Deep Dive: Terraform Remote Backend State Architecture

### 1.1 The Problem with Hardcoded S3 Bucket Names
In standard multi-module Terraform repositories, each module declares its remote backend inside `providers.tf`:
```hcl
# Problematic Hardcoded Approach
terraform {
  backend "s3" {
    bucket = "cleanmybelly-tfstate-v1-8b543648" # Mutates Git code!
    key    = "cleanmybelly/infra/environments/dev/backend/terraform.tfstate"
    region = "us-east-1"
  }
}
```
If the bucket name is hardcoded or injected via *find & replace*, every developer setup modifies tracked `.tf` files, polluting `git diff` and creating merge conflicts.

### 1.2 The Solution: Partial Backend Configuration
Terraform natively supports **Partial Configuration**. Static attributes remain in `providers.tf`, while dynamic parameters (the bucket name) are supplied at runtime via an unversioned `.tfbackend` file:

```hcl
# providers.tf (Committed to Git - Clean & Immutable)
terraform {
  backend "s3" {
    key          = "cleanmybelly/infra/environments/dev/backend/terraform.tfstate"
    region       = "us-east-1"
    use_lockfile = true
  }
}
```

```hcl
# backend.tfbackend (Generated by env-sync - Git Ignored)
bucket = "cleanmybelly-tfstate-v1-8b543648"
```

```bash
# Runtime Execution
terraform init -backend-config=backend.tfbackend
```

## 2. Deep Dive: The `!` Prefix in the `.env` DSL

### 2.1 Distinction: Input Variables vs. Backend Configuration
Terraform has two completely distinct concepts:
1. **Input Variables (`var.xxx`)**: Declared in `variables.tf`, defined in `terraform.tfvars`, used inside resources (`main.tf`).
2. **Backend Configuration**: Evaluated by the Terraform CLI before HCL evaluation starts. Backend parameters are **NOT** variables and cannot be declared in `variables.tf`.

### 2.2 How the `!` Prefix Works
In centralized `.env` files:
* Variables without prefix (`project_name = "cleanmybelly"`) are recognized as **Input Variables**. `env-sync` declares them in `variables.tf` and writes them to `terraform.tfvars` / `terraform.tfvars.example`.
* Variables with the `!` prefix (`!terraform_state_bucket = "cleanmybelly-tfstate-v1-remote"`) are recognized as **Backend Variables**. `env-sync` directs them exclusively to `backend.tfbackend` and `backend.tfbackend.example`. They are **never** declared in `variables.tf` or `terraform.tfvars`.

```text
.env Line                    Prefix Detection    Propagation Target
------------------------------------------------------------------------------------------
project_name = "..."       --> No prefix     --> variables.tf + terraform.tfvars (.example)
!terraform_state_bucket = "..." --> '!' detected  --> backend.tfbackend (.example) ONLY
```

## 3. Deep Dive: Why It is Called `bucket` in `backend.tfbackend` vs `!terraform_state_bucket` in `.env`

### 3.1 HashiCorp Terraform S3 Provider Specification
Terraform's S3 backend provider has a fixed, reserved schema defined by HashiCorp. The S3 backend only recognizes exact HCL keys:
- `bucket` (Required: name of the S3 state bucket)
- `key` (Path to `.tfstate`)
- `region` (AWS region)
- `use_lockfile` (Native S3 locking)

If `backend.tfbackend` contained `terraform_state_bucket = "..."` or any custom name, `terraform init` would fail with:
```text
Error: Invalid backend configuration argument
The backend configuration key "terraform_state_bucket" is not recognized by the S3 backend.
```

### 3.2 The Translation Bridge
* In `.env`, human developers write descriptive, self-documenting directives: `!terraform_state_bucket = "my-bucket-name"`.
* `env-sync` acts as a compiler bridge: it reads `!terraform_state_bucket` (or `!bucket`), extracts the value `"my-bucket-name"`, and formats the exact HCL line required by Terraform:
  ```hcl
  bucket = "my-bucket-name"
  ```

## 4. Deep Dive: Leaf Autodiscovery & The Local State Exception (`bootstrap`)

### 4.1 Leaf Module Autodiscovery Criteria
The `env-sync` lexer (`tools/modules/env_sync/lexer.py`) dynamically scans `aws/` without hardcoded lists. A directory is an indexed leaf module if:
1. It contains at least one `.tf` file directly.
2. It contains no child subdirectories with `.tf` files.
3. It is not inside `.terraform/`, `__pycache__/`, or hidden directories.

### 4.2 Why `aws/pre-infra/bootstrap` Uses Local State
- `aws/pre-infra/bootstrap` is the foundation module whose sole purpose is to **create the S3 remote state bucket in AWS**.
- Because the bucket does not exist prior to executing `bootstrap`, `bootstrap` must run with **local state** (`terraform.tfstate` on local disk).
- `env-sync` dynamically analyzes `providers.tf` in each leaf module via `has_s3_backend()`:
  - If a module has `backend "s3"`: `env-sync` generates `backend.tfbackend` and `backend.tfbackend.example`.
  - If a module lacks `backend "s3"` (like `bootstrap`): `env-sync` automatically excludes it from `.tfbackend` generation.

## 6. Multi-Directional & Lateral Synchronization Protocol

1. **Lateral Sync (`.env` <==> `.env.example`)**: Guarantees template blueprints committed to Git mirror every active `.env` variable with empty `""` values.
2. **Reverse Sync (Modules ==> `.env` & `.env.example`)**: Discovers variables declared directly in `variables.tf` or `terraform.tfvars` and injects them under `[module_token]` in both `.env` and `.env.example`.
3. **Forward Sync (`.env` ==> Module Files)**: Populates `terraform.tfvars`, `terraform.tfvars.example`, `backend.tfbackend`, `backend.tfbackend.example`, and auto-declares missing variables in `variables.tf`.
