# Reference: Infrastructure Directory & State Standards

This reference document outlines the directory structure, environment segregation, state key hierarchy, and architectural conventions for the **cleanmybelly** infrastructure codebase under `/aws/infra`.

---

## 2. Segmentation Strategy

### Dev vs. Prod Environment Isolation
* **State Keys**: Development (`dev`) and production (`prod`) environments use different S3 state keys.
* **Naming Prefixes**: Resources use distinct prefixes (e.g. `cleanmybelly-dev-*` vs `cleanmybelly-prod-*`).
* **Variable Isolation**: Region, scaling capacities, and domain names are configured per environment in `variables.tf` and populated dynamically from `environments/` via `env-sync`.

### Frontend vs. Backend Decoupling
* **Decoupled State**: Backend (Lambda, API Gateway, DynamoDB) and Frontend (S3 static bucket, CloudFront) have separate Terraform state files. Visual frontend updates do not alter compute/database infrastructure.
* **Remote State Cross-Referencing**: Frontend configurations pull API Gateway URLs dynamically using `terraform_remote_state` data sources parameterized by `var.terraform_state_bucket_name`.

## 3. Remote State Key Hierarchy & Partial Backend Configuration

All infrastructure states (except `aws/pre-infra/bootstrap` which creates the bucket) use the S3 backend with native state locking (`use_lockfile = true`). The `bucket` parameter is injected dynamically at initialization via `backend.tfbackend` generated by `tools/env_sync.py`:

```bash
terraform init -backend-config=backend.tfbackend
```

| Component / Layer | S3 Remote State Key | State Storage Type |
| :--- | :--- | :--- |
| **Bootstrap S3 Storage** | *(Local State `terraform.tfstate`)* | Local State |
| **IAM Local Deployer** | `cleanmybelly/pre-infra/iam-deployer/terraform.tfstate` | S3 Remote State |
| **GitHub Repository** | `cleanmybelly/pre-infra/github/repository/terraform.tfstate` | S3 Remote State |
| **GitHub OIDC Trust** | `cleanmybelly/pre-infra/github/oidc/terraform.tfstate` | S3 Remote State |
| **GitHub Secrets & Workflow** | `cleanmybelly/pre-infra/github/secrets-workflow/terraform.tfstate` | S3 Remote State |
| **DNS Zone** | `cleanmybelly/infra/shared/networking/dns-zone/terraform.tfstate` | S3 Remote State |
| **SSL Certificates** | `cleanmybelly/infra/shared/networking/terraform.tfstate` | S3 Remote State |
| **Dev Backend** | `cleanmybelly/infra/environments/dev/backend/terraform.tfstate` | S3 Remote State |
| **Dev Frontend** | `cleanmybelly/infra/environments/dev/frontend/terraform.tfstate` | S3 Remote State |
| **Prod Backend** | `cleanmybelly/infra/environments/prod/backend/terraform.tfstate` | S3 Remote State |
| **Prod Frontend** | `cleanmybelly/infra/environments/prod/frontend/terraform.tfstate` | S3 Remote State |

## 4. Cross-State Reference HCL Example

Frontend code references backend and networking outputs dynamically without hardcoded bucket names:

```hcl
data "terraform_remote_state" "backend" {
  backend = "s3"
  config = {
    bucket  = var.terraform_state_bucket_name
    key     = "cleanmybelly/infra/environments/dev/backend/terraform.tfstate"
    region  = "us-east-1"
    profile = "terraform-user"
  }
}

data "terraform_remote_state" "networking" {
  backend = "s3"
  config = {
    bucket  = var.terraform_state_bucket_name
    key     = "cleanmybelly/infra/shared/networking/terraform.tfstate"
    region  = "us-east-1"
    profile = "terraform-user"
  }
}

# Reference syntax in module resources:
# data.terraform_remote_state.backend.outputs.api_gateway_url
# data.terraform_remote_state.networking.outputs.hosted_zone_name
```
